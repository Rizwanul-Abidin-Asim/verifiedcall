Technical architecture

VerifiedCall

An AI agent that intercepts authorised push payment fraud by reading mobile-network signals, then phoning the customer in their own language before the money settles.

Team antifraud GSMA MENA Ignite Hackathon Theme 4 · Secure Fintech, Payments & Anti-Fraud Pillar · Connectivity for Good

Request path

How a payment reaches the network

The payment gateway holds the transaction and hands it to us. The agent decides which network signals are worth their latency, and only those are pulled — in parallel, behind a 3-second timeout.

Decision path

What happens to the signals

The model orchestrates and explains. It does not produce the risk number — a deterministic engine does, from a weighting table a compliance officer can read. The same transaction always scores the same.

The distinction that matters

Theft and coercion look identical until you ask where the phone is

These two cases produce the same signals: SIM swapped, calls forwarded, device roaming, a large payment to a first-time payee. One is somebody stealing an account. The other is a real customer being talked into it. They need opposite responses — and no single API can tell them apart.

Division of authority

What the model decides, and what it does not

A regulator has to be able to reproduce a payment decision. "The model produced that number" is not an acceptable answer, so the model's authority stops at the score.

DecisionOwnerWhy
Which signals to pull LLM agent Genuine orchestration. On a routine payment to a known payee it pulls none at all, and says why — that is the difference between an agent and a checklist.
The written explanation LLM agent Prose is what a language model is actually good at, and the reasoning trace is read by analysts, not machines.
The risk score Scoring engine Reproducible and auditable. Weights sit in one table that a compliance officer can review at a glance.
The outcome Scoring engine Derived from the score plus one policy rule about whether the customer is present.
Overriding a decline Policy guard rail If the model recommends declining while the customer is demonstrably present, policy holds the payment for a call instead, and records the disagreement. A false decline harms a real customer and does nothing to stop the coercion.
Insisting on evidence Policy guard rail If a transaction scores in the decline band but the agent skipped the location check, the engine pulls it. We never decline without the evidence that justifies declining.

How the components communicate

End to end, in six steps

  1. Merchant checkout → Decision API. The payment gateway posts a webhook for a submitted transaction to POST /transactions/evaluate, and the payment is held pending a decision.
  2. Decision API → Risk agent. The transaction is persisted, then handed to the Pydantic AI agent together with its context: amount, whether this beneficiary has ever been paid before, and the local time.
  3. Risk agent → Agent tools → CAMARA client. The agent autonomously selects which network signals justify their latency and calls them through the tool layer. The agent itself issues no HTTP.
  4. CAMARA client → Nokia Network as Code. The selected signals are queried in parallel behind a 3-second timeout. Any failure degrades to a cached response that stays visibly labelled as cached.
  5. Scoring engine → Outcome. Observed facts become a 0–100 score, an outcome, and a numbered reasoning trace — deterministically, with the policy guard rails applied.
  6. Voice layer → Decision log → Console. A held payment triggers an outbound call in the customer's language; the outcome resolves the transaction, and every signal, decision and transcript streams to the fraud-ops console.
Measured, not projected. All four CAMARA APIs are integrated and verified live against the Nokia sandbox. Four signals pulled concurrently complete in 541 ms; a clean payment reaches a decision in roughly 1.2 s end to end, having pulled no network signals at all. 53 automated tests run with no API key and no network access.
